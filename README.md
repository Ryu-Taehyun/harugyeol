# 하루결 · Plan–Do–See 다이어리

아이디를 만들어 로그인하면 날짜별 계획, 실행, 회고를 기록할 수 있습니다. 최초 계획 규칙과 한 차례의 변경 이력을 계정에 저장합니다.

- GitHub Pages 안내 화면 · https://ryu-taehyun.github.io/harugyeol/
- 로컬 로그인 및 다이어리 · http://127.0.0.1:3000
- 회원가입과 기록 저장은 서버 실행 환경에서 제공됩니다. 과제의 온라인 결과물 URL에는 서버 배포 후 실제 서비스 주소를 적습니다.
- 소스 · 이 프로젝트에 앱, 데이터베이스 스키마, 검증 스크립트를 함께 제공합니다.
- 제출 자료 · [검증 근거](docs/verification.md)와 [5일 실사용 기록 양식](docs/five-day-log.md)

## 실행 방법

Node.js 24 이상에서 압축을 푼 폴더를 열고 아래를 실행한 뒤 http://127.0.0.1:3000 에 접속합니다. 외부 패키지 설치 없이 실행됩니다.

```text
node scripts/local.mjs
```

로컬 데이터는 실행 시 생성되는 `data/harugyeol.sqlite`에 저장됩니다. 배포 환경에서는 같은 SQL 스키마를 D1에 적용합니다.

## 인증 구현 설명

### ① 무엇으로 구현했나

회원가입과 로그인에 아이디와 비밀번호를 사용했습니다. 비밀번호마다 16바이트의 무작위 salt를 생성해 PBKDF2-HMAC-SHA-256을 600,000회 적용합니다. 세션에는 32바이트 무작위 토큰을 사용하며 DB에는 토큰의 SHA-256 해시와 만료 시간을 저장합니다. 브라우저에는 `HttpOnly`, `SameSite=Lax`, HTTPS에서 `Secure`가 설정된 7일 쿠키를 발급합니다.

### ② 왜 선택했나

로그아웃 즉시 세션을 폐기하려고 서버 저장형 세션을 선택했습니다. Web Crypto의 표준 API로 비밀번호 해시를 만들고, SQL의 소유자 조건으로 사용자마다 독립된 기록을 조회하고 변경합니다.

### ③ 어디를 어떻게 수정했나

| 위치 | 구현 |
| --- | --- |
| `worker.mjs`의 `authenticate`, `session` | 비밀번호 검증, 세션 발급·회전·만료, 인증 요청 횟수 제한 |
| `worker.mjs`의 `fetch`, `diaries`, `rules` | 보호 화면 리다이렉트, 로그아웃 시 세션 삭제, 기록 소유권 검사, 규칙 변경 일시 제한 |
| `drizzle/0000_diary.sql` | 사용자·세션·다이어리·규칙·요청 제한 테이블과 계정별 날짜 유일 제약 |
| `web/login.html`, `web/diary.html`, `web/main.js` | 가입·로그인, 기록 작성·조회·수정·삭제, 5일 진행 상황, 규칙 변경 이력 |
| `scripts/auth.test.mjs` | 두 임시 계정을 이용한 마스킹 검증과 요청·응답 출력 |

### ④ 접근이 차단되는 것을 어떻게 확인했나

로컬에서 서버 요청을 실행해 로그인 전 보호 화면의 `303 /login`과 API의 `401`을 확인했습니다. A와 B가 서로의 기록을 읽거나 수정하거나 삭제하는 경우는 양방향 모두 `404`였습니다. 각 계정 목록은 그 계정의 기록만 포함했습니다. B가 로그아웃한 직후 서버에 이전 쿠키를 다시 전달하면 `401`이 반환됐습니다. 요청·응답은 [검증 근거](docs/verification.md)에서 확인할 수 있습니다.

### ⑤ AI와 나

- AI에 맡긴 일 · 웹 UI, 서버 인증·인가, DB 스키마와 검증 코드를 작성했다.
- 내가 직접 판단한 일 · [직접 검토하고 채우기]
- AI 제안을 따르지 않은 일 · [직접 검토 후 결정 및 이유를 적기]

### ⑥ 아직 남아 있는 보안 한계

비밀번호 재설정, 다중 인증, 전체 기기 세션 관리 기능은 구현 범위 밖입니다. 로그인 시도 제한은 10분 고정 구간을 사용하므로 경계 시점에 요청이 집중될 수 있습니다. 로컬 실행은 루프백 주소에서 HTTP를 사용합니다. 다이어리 내용에는 애플리케이션 수준의 별도 암호화를 적용하지 않았으므로 DB 운영 권한도 관리해야 합니다.

## 짧은 확인 방법

- 어디로 가나요 · 로컬 주소에서 로그인 화면을 엽니다.
- 무엇을 하나요 · 가입하고 기록을 한 건 저장한 다음 로그아웃합니다.
- 무엇이 보이면 통과인가요 · 로그인 후 저장한 기록이 보이고 로그아웃하면 로그인 화면으로 이동합니다.
- 안 될 때 무엇이 보이나요 · 로그인 전 자료 화면은 `/login`으로 이동하고 자료 API는 `401`을 반환합니다. 다른 계정 자료를 요청하면 `404`가 반환됩니다.

## 5일 실사용 방법

처음에 **계획 규칙**을 저장합니다. **내 다이어리**에서 하루에 한 건씩 실제 계획, 실행, 회고를 기록합니다. 한국 시간으로 첫 기록을 저장한 날이 1일차입니다. 2일차 기록을 확인한 뒤, 3일차 00:00 전에 규칙 하나와 변경 이유를 저장합니다. 다섯 날짜의 기록과 규칙 이력을 [기록 양식](docs/five-day-log.md)에 정리합니다.

비밀번호, 세션 쿠키와 토큰, 비밀키는 제출 자료에서 마스킹합니다. 심사자에게 실제 계정 비밀번호를 제공하지 않습니다.
